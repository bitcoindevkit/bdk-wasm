# BDK dependency upgrade assessment

Checked against crates.io, npm, upstream release notes, and the resolved graphs on **2026-10-28**.

| Yarn | 4.12.0 | 4.18.1 |

The Rust and Node lockfiles also refresh transitive dependencies. CI actions are pinned to the current release commits, and wasm-pack downloads are checked against release SHA-256 digests. Node dependency install scripts are disabled.

Constraints on taking newer major versions:

- **BDK 3.2.0 is the latest stable wallet release and is adopted here.** Upstream master is already `4.0.0-alpha.0`, an unreleased development line; use the stable release rather than a moving Git branch. Its `bdk-tx` integration remains explicitly unstable (feature plus compiler flag); it is not enabled. Cargo.lock can include optional packages even when they are absent from the compiled feature graph.
- `bdk_esplora` 0.22.3 and the wallet resolve to the same `bdk_core` 0.6.4 and Bitcoin types. The wallet uses `bdk_chain` 0.23.4. Matching compatibility matters more than matching version numbers.
- `bitcoin` 0.32.102 is the highest non-yanked stable version reported by crates.io; 0.33.0-beta is a prerelease.
- The direct `getrandom` 0.2.17 dependency enables the JS entropy backend used by BDK's `rand` 0.8 / `rand_core` 0.6 graph. Replacing it with 0.4 would not enable that backend. The resolved rand 0.8.8 contains the relevant fix.
- TypeScript 7.0.2 is outside both ts-jest's `<7` and typescript-eslint's `<6.1` peer ranges. Keep TypeScript on 6.0.x until both tools support 7.
- BDK itself requires Rust 1.85; the refreshed ICU dependencies require **1.88**, which is this project's new tested MSRV. Node test tools require **22.13+ or 24+**; CI uses Node 24.

## BDK 2 to 3 migration

[BDK 3.0](https://github.com/bitcoindevkit/bdk_wallet/releases/tag/v3.0.0) changed descriptor templates to accept `NetworkKind`. The bindings convert only at that boundary and retain the concrete network for addresses and wallet state. Tests cover Bitcoin, testnet, testnet4, signet, and regtest.

The removed `include_output_redeem_witness_script` builder method remains as a compatibility no-op because BDK now includes those fields automatically. `cancel_tx` retains the BDK 2 behavior by unmarking wallet-owned outputs; outputs already observed in the transaction graph remain used. Events now use the crate-root `WalletEvent` export.

BDK 3 adds a defaulted `locked_outpoints` changeset field. Frozen JSON snapshots generated by BDK 2.3.0 verify loading, transaction history, derivation indices, balance, and signing after recovery. Keep a backup before upgrading persisted data. BDK promises reads from the previous major version; older software can ignore new fields, so rewriting state after downgrading may discard them. Lock-management bindings are not added in this upgrade. The changeset wrapper also rejects conflicting descriptors or networks before merging, avoiding upstream debug assertions and partial state changes.

[BDK 3.1](https://github.com/bitcoindevkit/bdk_wallet/releases/tag/v3.1.0) adds important previous-transaction validation and signing fixes. Regression tests exercise mismatched previous transactions, conflicting witness amounts, missing previous transactions, conservative sighash defaults, opt-ins, watch-only recovery, and separate finalization.

[BDK 3.2](https://github.com/bitcoindevkit/bdk_wallet/releases/tag/v3.2.0) deprecates wallet-owned signing and key extraction. `SignOptions` itself remains supported. The existing JavaScript signing/load API is preserved with two narrow deprecation allowances; designing caller-owned signer bindings is tracked in [#15](https://github.com/bitcoindevkit/bdk-wasm/issues/15). Replacing it with a bare `Psbt::sign` call would require preserving wallet checks, options, and finalization semantics.

## Advisory results and remaining work

Before the refresh, Cargo.lock reports:

- [RUSTSEC-2026-0007](https://rustsec.org/advisories/RUSTSEC-2026-0007.html): bytes integer overflow.
- [RUSTSEC-2026-0190](https://rustsec.org/advisories/RUSTSEC-2026-0190.html): anyhow mutable downcast unsoundness.
- [RUSTSEC-2026-0097](https://rustsec.org/advisories/RUSTSEC-2026-0097.html): rand logger/reseeding unsoundness.
- [RUSTSEC-2026-0386](https://rustsec.org/advisories/RUSTSEC-2026-0386.html): tokio AsyncFd I/O unsoundness.

The refreshed Rust lockfile passes `cargo audit --deny warnings` without exceptions. These are lockfile findings, not proof of exploitability in the WASM artifact.

The updated Node test-tool graph retains two documented findings in [#56](https://github.com/bitcoindevkit/bdk-wasm/issues/56): unpatched `deepmerge@4.3.1` (GHSA-gcqx-w48m-w2h4, low severity) and the `glob@10.5.0` publisher deprecation notice through Jest's coverage tooling. CI allows only their exact advisory IDs; packages and severity levels are not excluded. Run `YARN_NPM_AUDIT_IGNORE_ADVISORIES=none yarn npm audit --all --recursive` to see the full report. These tools are not dependencies of the generated WASM packages.

The binding review also fixes Node/worker Esplora retry timers, removes the unsafe Send assertion using a Rust oneshot receiver, rejects fee-rate overflow with a recoverable JavaScript error, and rejects unsupported fee-bump options that were previously ignored ([#57](https://github.com/bitcoindevkit/bdk-wasm/issues/57)). These checks and dependency scans do not establish absence of all defects or replace an independent security review.

## Reproduction

Use `bash scripts/install-wasm-pack.sh` and Rust with the `wasm32-unknown-unknown` target. On macOS, use the LLVM environment described in DEVELOPMENT.md.

```sh
cargo fmt --all -- --check
cargo clippy --locked --all-features --all-targets -- -D warnings
cargo audit --deny warnings
cargo +1.88.0 check --locked --all-features --all-targets
cargo +1.88.0 check --locked --all-features --target wasm32-unknown-unknown
wasm-pack test --chrome --firefox --headless --features debug,default --locked
wasm-pack test --chrome --firefox --headless --features debug,esplora --locked
cd tests/node
yarn install --immutable
yarn build
yarn typecheck
yarn lint
yarn jest --runInBand --testPathIgnorePatterns='integration/(esplora|events)'
yarn npm audit --all --recursive
cd ../..
bash tests/run-integration.sh
```

Browser tests use deterministic old-wallet fixtures and a mocked transient HTTP failure. Regtest verifies the real HTTP and Bitcoin Core transaction paths. The existing main-branch signet smoke test remains a separate live-network check.
